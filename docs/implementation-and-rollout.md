# CamDiag implementation and rollout, 2026-09-23

## Implemented in the working tree

The app uses verified clinician claims and an active server-managed membership for clinical access. Profile roles cannot grant access. Firestore and Storage block client writes to authoritative encounters, source manifests, OCR, analyses and reviews. The API records versioned clinical consent and enforces triage, one current source manifest per encounter, reviewed transcription, quotas, and review state. Sign-off is allowed only once for the latest analysis of the current transcription and source. The backend creates idempotent jobs with leases, deadlines and bounded retry. Private uploaded pages have a 24-hour source expiry and a scheduled purge. Analysis records source hashes, model/prompt/schema versions and requires clinician sign-off. Medication endpoints return **not assessed** without governed evidence; interaction queries are limited to ten medicines and six calls per minute to avoid a costly or misleading partial assessment.

The browser keeps clinical state in memory only and clears it on UID/authority changes, logout and invalid sessions. Uploads support progress, cancellation and recovery from saved encounters. Original pages are shown beside OCR correction; missing source blocks attestation. Public pages no longer claim autonomous, offline or validated diagnosis. The demo uses a fixed synthetic example. PDF is offered through print/save PDF, with saved provenance, limitations and review status. Analytics is optional, defaults off and only reports allowlisted events on public routes. The service worker caches a small offline notice and never caches patient data or forces a consultation reload.

The manual release workflow builds frontend and Functions, runs frontend/backend/rules/browser checks, deploys Firebase Hosting, Functions, Firestore indexes/rules and Storage rules, then probes web/API readiness. The reviewed canonical web origin is `https://camdiag-c7e78.web.app`; Android currently points there. App Hosting remains a secondary legacy surface until its availability and policy parity are checked. See [release assurance](./release-assurance-register.md) for unsigned human approvals.

## Before production release

1. Investigate the existing live API 500 and App Hosting 5xx. The read-only checks on 2026-09-23 showed the API Cloud Run revision Ready and billing enabled, with no matching system error log entries. Inspect scoped runtime logs through an approved incident process, avoiding patient content in tickets. Confirm a fresh backend `/health` and `/ready` response, then run `npm run smoke` against the deployed revision.
2. Obtain the signed clinical validation, privacy impact, regulatory classification, data residency, security risk and clinical safety approvals in the release register. Configure the `production` GitHub environment reviewers and `CLINICAL_RELEASE_APPROVED` repository variable from those records. A manual `approval_reference` is required for deployment.
3. Review actual clinician identity and organization membership. The dry-run administrative utility is `npm run access:clinical -- --project=PROJECT --uid=UID --action=grant --organization=ORG --role=doctor --approver=ACTOR --reference=APPROVAL_RECORD`. Only an authorized operator with approved credentials may append `--apply`. Revoke access by using `--action=revoke` and the same audit fields. Do not self-approve test or real accounts. Verify that the membership, custom claims and refresh token revocation agree.
4. Review and back up existing Firestore/Storage data. The new authoritative encounter model intentionally does not rewrite legacy `scans`/`patients`. Legacy records remain exportable but are immutable from clients. Inventory legacy base64 profile photos and move them to an approved secure media path or remove them through a controlled migration; permitted profile edits now work even if an unchanged legacy photo field is present. Confirm retention and deletion handling for Firestore, logs, backups and providers with the privacy lead.
5. Configure Firebase Storage CORS on the browser upload bucket using [storage-cors.json](../storage-cors.json); verify it contains the canonical origin and upload/download methods. This bucket setting is outside Firebase rules deployment and requires an authorized Cloud Storage operator. Verify App Check enforcement, bucket lifecycle, source purge scheduler, Firestore TTL/index build completion, service account IAM, runtime parameter values and cost alerts in staging before production.
6. Establish approved pharmacist-reviewed medication evidence documents with version, citation, review date and expiry. Without them, medication results correctly remain **not assessed**. Validate English and French clinical wording with reviewers; Pidgin mode explicitly uses English for clinical results pending validation.
7. Run a frozen de-identified source set through OCR and interpretation. Measure dangerous substitutions, decimal/unit/allergy misses, review burden, false reassurance and failures under weak connectivity. Block release on unresolved safety defects. Verify device camera and Android wrapper behavior on real hardware.

## Local verification commands

`npm run scan:secrets`, `npm run lint`, `npm run typecheck`, `npm test`, `npm test --prefix functions`, `npm run test:ops`, `npm run test:rules`, `npm run test:e2e`, `npm run build`, `npm run build --prefix functions`.

The Playwright fixture bypass is restricted to development on localhost and targets only `http://localhost:5175/__test_api`. It cannot authorize production requests. On Windows, the bundled Playwright web-server teardown may leave a child process alive; a local external Vite server can be used with `CAMDIAG_E2E_EXTERNAL_SERVER=true`. The rules test helper keeps Firebase emulator binaries in the ignored local `audit-output/emulator-cache/` directory. CI runs on Linux. The release workflow still needs a full staging rehearsal before use.

The dependency advisory scan was not run. Automatic approval review rejected `npm audit` because sending the private package/version tree to npm was not specifically authorized. No alternate upload route was used. Explicit approval of that metadata disclosure is needed for this check.
